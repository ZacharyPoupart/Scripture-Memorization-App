# Memorize For Life — project context for Claude Code

Read this first. It holds the goals, the rules that have caused the most bugs, how to run/test things, and our working agreements.

## Goal
Make Scripture memory a consistent daily habit and make verses stick for life. A verse is practiced heavily when new, then reviewed less and less as it becomes solid, never forgotten. Used mainly on an iPhone (installed to the home screen, full screen) and also on a computer. Clean, calm, focused, fast; no jumpy screens, no stuck buttons. Must work completely offline once installed; only verse lookup and sync need a connection. User data must never be lost. Simple for the owner to host and update.

## Stack
Preact + TypeScript + Vite, installable PWA (vite-plugin-pwa / Workbox). Data in IndexedDB (localStorage fallback). Optional sync: a Cloudflare Pages Function + KV storing one end-to-end-encrypted blob per link code. Hosting: Cloudflare Pages (Git integration). Tests: Vitest (unit) + Playwright (e2e, Chromium).

## Layout
- `src/core/` — **pure logic, no DOM**. `schedule.ts` is the heart (piles, due dates, spacing, graduation, progress days, streak). Also `dates.ts`, `merge.ts` (sync merge), `backup.ts` (export/import validation), `quiz.ts`, `speech.ts`, `text.ts`, `books.ts`, `reference.ts`, `versification.ts` (generated), and read-only helpers that never affect scheduling: `stats.ts` (streak history, heatmap, totals), `milestones.ts`, `organize.ts` (search/sort/filter/topic rename), `nudges.ts`.
- `src/services/` — `storage.ts` (IndexedDB, atomic saves + snapshots), `lookup.ts` (verse text APIs), `sync.ts` + `syncCrypto.ts`, `feedback.ts` (optional quiet sound; off by default).
- `src/store.ts` — app state; all mutations go through `act()` (clone → settle days → mutate → save → schedule sync).
- `src/ui/` — screens; `src/ui/modes/` — the review modes and reference recall.
- `functions/` — Cloudflare Pages Function for sync (`functions/_lib/sync.js` is shared with the e2e server).
- `tests/unit/` (Vitest, TZ pinned to America/New_York), `tests/e2e/` (Playwright; `helpers.ts` has `saved(page)`, `replaceDataWith`, `localDay`) and `tests/fixtures/` (real v1.1.0 export + settings used by `migration.test.ts`).
- `DECISIONS.md` (what changed and why, test changes, open questions) and `docs/IOS-CHECKLIST.md` (manual iPhone checks).

## THE RULES (single source of truth: `src/core/schedule.ts`; these bugs bit us before)
- **Days** are local calendar days (`YYYY-MM-DD`) and roll over at local midnight. Day math uses UTC day numbers so DST never causes off-by-one. Never compare timestamps to decide "same day"; use `dayKeyOf`.
- **Daily pile**: 3 *counted* reviews per day, at least `spacingHours` (default 2; Settings offers No wait, 30 min, 1–4 h or a custom number of minutes, stored as hours 0–12) apart. Spacing resets at midnight (the first review of a new day is always available).
- **Weekly / Monthly / Yearly (calendar, v1.33.0, owner-requested)**: one counted review in each calendar week (Sunday to Saturday), month or year; reviewed any time in the period = good until the next one starts (`periodStart`/`periodEnd`, `dueDay(v, day)`). Everything is due on the period's last day: that is the only day an unreviewed one breaks the streak (the verse shows as ready all period, and Today never calls it missed before then). Only the week a verse arrives in from Daily is a free pass; a verse that moves up to Monthly or Yearly must be reviewed in the month/year it arrives (reviews on the move day belong to the old pile, so only later days count; a verse moved on a period's last day is exempt that day like any new verse).
- **Extra practice** is always allowed and never counted or stored for the schedule, but a per-device weekly tally of it (`data.extraWeek`, v1.51.0, owner-requested) counts toward a guild's weekly goal (shared as `extra`; it earns no coins) (a Weekly, Monthly or Yearly pile page has a one-tap "Review all" when nothing is due, v1.47.0, owner-requested); it only marks the day as "reviewed" and never earns a progress day.
- **Graduation**: Daily→Weekly after 90 progress days, Weekly→Monthly after 15 reviewed weeks, Monthly→Yearly after 6 reviewed months (`GRADUATION_DAYS`, counted in `PROGRESS_UNIT`s; the ring says "Week 7 of 15"). Yearly is permanent. A progress day (Daily) is a day after entering the pile with one counted review. Weekly/Monthly count whole periods: a review any time in the week/month earns it at once (the days still ahead included), a skipped one earns nothing and is never made up, no freeze. Stored per verse as `Verse.prog` (day offsets from `pileSince`, merged by union while pile+pileSince match; older data is filled once from the ledger with the legacy rule so earned progress is kept; weekly/monthly progress is the number of distinct periods in it, the free arrival week excluded). Graduation happens on the review that earns the last day/period (`promotionDay`: the first review of the period that reached the target) and can cascade through several piles in one settle. The level-up id is deterministic (`verseId:to:day`) so devices agree.
- **Manual moves** (with undo) set `pileSince = today` (progress restarts) unless the owner uses "Start partway" (v1.10.0): `movePile(…, daysIn)` / `addVerse({daysInPile})` back-date `pileSince` by N whole days, clamped to `maxDaysIn` (89 Daily, 91 Weekly, 120 Monthly, 366 Yearly), so progress and due dates follow the normal rules from that earlier start. A verse added with history counts as an obligation today; a brand-new one (N=0) still doesn't.
- **Ordering**: within a pile, longest in the pile (`pileSince` ascending) first by default; the sort a person picks on the Piles and pile pages (`settings.listSort`, device-only, v1.59.0, owner-requested) is remembered across visits and launches, while search and filters start fresh each launch. Today's and a pile's review sessions visit verses in that order unless the device setting `settings.shuffle` (the small shuffle button beside the review-type bar, off by default, v1.32.0) is on, which only randomizes the order a session visits them in (`shuffled` in `core/today.ts`, applied in `Review`; a single chosen verse is still one verse); what is due and what counts never looks at it.
- **Move down (v1.33.0, owner-requested)**: a Weekly/Monthly/Yearly verse that needed two restarts (`STRUGGLE_RESTARTS`, wrong answers in a review that allows none) and still counted is offered, on the result card, a move to the pile below (`easierPile`); the owner chooses ("Move to Daily" / "Keep it in Weekly"), a toast offers Undo, nothing is ever moved automatically. Moving to Daily puts the verse back with only a week to go (`moveDownDaysIn`: 83 of 90 days credited, v1.45.0, owner-requested); a move to Weekly or Monthly is a normal manual move (progress restarts). Not offered on the review that levelled the verse up.
- **Streak forgiveness (v1.54.0, owner-requested)**: once per calendar month, the first missed day (`o:'m'`) that would break a live streak (a streak of at least one complete day behind it) is forgiven (`forgivenDays` in `schedule.ts`, from `FORGIVENESS_START` 2026-10-28 on; earlier history is untouched). It is derived from the ledger every time, never stored, so devices agree whatever order they sync in. A forgiven day is neutral like a day with nothing due: it adds nothing to the streak, earns no progress day, and `streakInfo`/`streakRuns` skip it; the ledger still says `'m'`. Stats shows it in gold (`CellKind` `saved`); a one-time popup (`ui/StreakSaved.tsx`, device setting `seenSaved`) tells the owner. No data shape change.
- **Streak**: +1 for each day on which every due verse got at least ONE counted review (Daily's goal is still 3 a day, but one keeps the flame; changed by the owner's request in v1.5.2). Practising on a day when nothing was due (e.g. the first day) also earns it. A due verse with no review breaks it; days with nothing due and no practice are neutral. Verses added or moved *today* are exempt today ("brand-new verses don't count against me"). Longest streak is tracked and merged with max.
- **Break (pause, v1.9.0, owner-requested)**: Settings → Take a break sets `data.pause = {from, until, at}` (synced, last-writer-wins by `at`; absent = never used). On paused days nothing is due and nothing can be missed: `settle()` writes `{o:'n', p:1}` (or `'c'` if the user reviewed everything due anyway; never `'m'`), so the streak waits and there is no lapse; but a paused day earns **no progress day** unless the user reviewed (`dayCounts`), so nothing graduates on holiday. Due dates are not moved. Reviewing anyway is always allowed and counts normally. Additive optional fields only (`pause`, ledger `p`): `schema` stays 1; `tests/fixtures/backup-v1.9.0-pause.json` covers it.

## Data safety
Every save is ONE atomic write (new data + `data.prev` + once-a-day snapshot, 7 kept); don't add reads or extra steps in front of it. Imports validate everything (`normalizeData`) and **merge by default** (replace is explicit and undoable). Never change the on-disk shape without bumping `schema` and writing a migration + tests; `tests/unit/migration.test.ts` + `tests/fixtures/*-v1.1.0.json` must stay green forever (add a new fixture whenever the shape changes). New device-only preferences go in `Settings` with a default (older saved settings load by layering over defaults). Test hooks on `window.__mfl` (`getState`, `flush`, `crash`) exist for e2e only.

## Design guard rails
The look: the original calm teal-and-paper colours (the owner tried the warm "Hearth" colours in v1.21.0 and went back in v1.22.0), with Fraunces for the verse and headings and Nunito for everything else (both bundled in `public/fonts`, so it looks the same offline), rounded cards and pill buttons. Today (`ui/Home.tsx`) is deliberately bare: no date or greeting, no progress ring, the review-type bar (Flashcard / Blanks / Type / Speak) at the top of the card, the four piles as one quiet row at the very top (v1.46.0, owner-requested), the day's verses as the hero (each row is a button that opens `/review?verse=<id>` for just that verse, in the remembered type, v1.58.0, owner-requested); during a review the type name in the header is a button that swaps the type (the verse in front of you starts over in the new type and the rest of the session uses it); the type you last chose, on Today, the pile page, a verse's page or in a review, is remembered as `settings.defaultMode` and used next time, and Settings has no separate default-type choice (v1.42.0, owner-requested); keep generous spacing and cut words rather than add them: what the guided tour already explains is not repeated in a screen's help text, and self-explanatory disclaimers are left out (v1.41.0, owner-requested; warnings that protect data, and the children's note on Friends, stay). The browser/status-bar colour (`theme-color`) is kept in step with the page's own `--bg` by `applyTheme` in `store.ts` (one meta tag, no media query, v1.60.0), so the phone's light/dark setting alone never paints a different strip above the page. Palette/type live in `src/styles.css` tokens; `tests/unit/contrast.test.ts` enforces WCAG AA in both themes and no pure black/white (change colours there, never ad hoc). Celebration pop-ups (level-up, streak milestone, streak saved, new item) close with a × in the corner (`CloseX`), a tap outside or Escape, never a thank-you button (v1.55.0, owner-requested); Toasts appear at the top and are non-blocking; the primary action lives in the bottom `.action-bar`; hover styles only for real pointers. No guilt/urgency wording (an e2e test scans for it); missed days look like rest days in the heatmap.

2. Change only what was asked. If something else looks wrong, **tell the owner instead of fixing it silently**.
3. Run the tests before committing. Add or update tests for anything you change (rules changes need unit tests first).
4. Small, focused commits with clear messages.
5. Open a pull request summarising what changed, how it was tested, and the version bump (use the PR template). **The owner has delegated merging to Claude's discretion:** merge only on a fully green CI (never skipped/weakened tests), one PR per stage, then add a stage tag with the Tag workflow, and tell the owner what shipped and how to undo it. The owner can still ask for a revert or a hold at any time.
6. If a release causes problems, **roll back first, then fix**.

## Releases and rollback
Tags: `release.yml` adds `vX.Y.Z` when a version bump merges; the sandbox can't push tags, so stage tags (`v1.2.0-ui`, `v1.1.0-stable`, …) are created by the add-only `tag.yml` workflow (run it with the tag, a full commit sha on `main`, and a message). Semantic versioning in `package.json` (shown in the app via `__APP_VERSION__`). Each PR that ships changes bumps the version and moves notes from `## [Unreleased]` in `CHANGELOG.md` (`npm run release -- patch|minor|major`). Merging to `main` deploys via Cloudflare Pages and `.github/workflows/release.yml` tags `vX.Y.Z` + creates a GitHub release. Rollback: see README ("Rolling back").

## Secrets
None are needed to build, test or run. Never commit keys; use environment variables / gitignored `.env` (see `.env.example`). The only runtime secret is the optional `API_BIBLE_KEY` (Cloudflare secret) used by `functions/api/verse.js` for NIV lookup; the client never sees it. If a key is ever pasted into chat or committed, tell the owner to rotate it.

## Known limitations / things to verify on a real iPhone
- Verse lookup uses free public APIs (bible-api.com for KJV/WEB, bolls.life for the rest); NIV goes through our `/api/verse` function (API.Bible, needs the owner's key and NIV access, with bolls.life as backup). API.Bible's terms may require copyright display and usage (FUMS) reporting — copyright text is returned by the function but not yet stored or shown, and FUMS reporting is not implemented; the owner should read their terms. They were coded to the documented response shapes but **not exercised against the live services from the build sandbox**; typing the text always works. Copyright of NIV/ESV/etc. text belongs to the publishers — fine for personal study, check terms before making the app public.
- "Speak it" uses the Web Speech API: experimental, behaviour on iOS home-screen apps varies.
- On iOS the on-screen keyboard may need a tap on the text to re-open between verses in "Type it out" mode.
- Playwright runs Chromium only (no WebKit): iOS Safari quirks need a real-device check on every preview.
